# Incident review implementation plan

The [agreed specification](spec.md) defines the behavior. The [task checklist](tasks.md) records dependencies and maps acceptance criteria to verification.

## Screen flow and layout

1. **Review.** At wide widths, show a queue on the left and the selected report on the right. On narrow screens, show one at a time with a **Back to queue** link. Existing Telegram links open the report directly. The report header shows status, a short summary, the main source, uncertainties, and any suggested match. An expandable **Sources and evidence** section holds excerpts and secondary details.
2. **Choose a decision.** Place the three named actions below the report summary. Open one action panel below them and move focus to its heading. Keep the report summary available while editing. Resolved reports show their decision and feedback in this space.
   - **Publish** opens the incident form, with core fields and references first and secondary fields grouped below. For a flagged match, show the reason and the separate-event decision before enabling publication.
   - **Update** opens a searchable published-incident picker. Show title and year to help distinguish results. Show the chosen target above the comparison, with **Change target** and **Revision history** nearby. Use columns for current and proposed values on wide screens and labelled pairs on narrow screens. Below the comparison, list supporting sources, include the reason field, and show a confirmation summary naming the target and selected changes before **Apply update**. A stale error appears above the comparison with **Reload and compare**.
   - **Reject** opens only the rejection form, including the existing duplicate reason and a separate **Reject report** submit button.
3. **Revision history.** Open a read-only panel from the current incident context, with newest revisions first. Each entry shows its timestamp and reason. Expand it to see before/after field values and added sources. Include an empty state. Returning to the comparison keeps its draft and confirmation if the target has not changed.
4. **Administration settings.** Link to a separate view from the review header. Give AI, Telegram, and workbook import their own headings. Reuse their existing controls and explicit actions.
5. **Outcome.** Show the saved action and links back to the queue and to the affected incident when applicable. If fetching fresh results fails, show the saved outcome beside a refresh retry.

## Technical approach

- Start with the local frontend changes in `AdminPanel.jsx`, `IncidentUpdateReview.jsx`, `IncidentUpdateComparison.jsx`, and the incident data helpers. Inspect their existing tests before moving components or changing review state. Keep the current React/Vite app, FastAPI, and SQLAlchemy.
- Extend the existing protected apply-update route and transaction. Require an explicit confirmation in the request bound to the selected incident ID and review version. Recheck pending status, eligible relationship, published target and version on the server. Include pending unclassified candidates. Preserve the separate-event approval guard. Add a server-side allowlist for the seven text fields, supporting sources, and the existing summary-to-description synchronization as a derived write. Validate source links and require a reason before applying changes.
- Reuse the source merger and revision snapshots. Verify that existing sources can be selected to support corrections without replacing their stored provenance. Use the current transaction and revision uniqueness constraint to keep the candidate decision, incident mutation, and single revision consistent. Check concurrent updates against the same incident and competing decisions on the same report. Where locking differs between PostgreSQL and SQLite, use a conditional write or equivalent database-level guard if required by the tests.
- Return a stable conflict response for a stale target or already-resolved report. The client can distinguish these from validation or connection failures. On reload, fetch current data, invalidate confirmation and selections, and wait for a manual decision.
- Add a read-only administrator endpoint for a published incident's revisions. Use existing revision rows and derive a display diff from snapshots and source additions. Limit the response to the fields needed for history. Verify legacy revisions render where snapshot fields are absent. No schema migration is expected with the current history table.
- Keep drafts in memory for the active review session, keyed by report and action. Clear target-derived state when switching context or reloading. Cancel or ignore outstanding requests for abandoned contexts, and keep each submit action within its own form. Reuse the existing settings controls, queue loading, direct links, and public refresh behavior.

## Compatibility and release checks

The apply-update contract will require confirmation and enforce a narrower field set. Update the bundled client and server together, verify whether any additional callers use that route, and have an already-open older client prompt a reload if it receives the missing-confirmation response. Keep public incident responses, deep links, ordinary create and edit paths, workbook import, and notification behavior compatible. Use synthetic records, disabled workers, and fake external clients. Verify SQLite and disposable PostgreSQL plus the bundled frontend and container checks before considering the feature ready. Confirm the revision migration is present in the target environment before an authorized rollout.
