# MCAD project overview

MCAD collects maritime cybersecurity reports for human review and presents published incidents on a public map and list. Public readers explore tracked events and their sources. Administrators curate the records, and Telegram subscribers can receive alerts. Incident eligibility and uncertainty rules live in the [draft domain rules](incident-selection-rules.md).

## Existing behavior

| Area | Implementation |
| --- | --- |
| Public website | React/Vite serves the map, list, filters, and incident details. Reports without coordinates remain searchable in the list. The UI reads published incidents through the FastAPI API. [Frontend entry](../frontend/src/App.jsx), [data client](../frontend/src/data/incidents.js), [API](../mcad/api.py) |
| Administration | The `/admin` interface loads the review queue using administrator bearer authentication. It supports editing proposal fields, rejecting with feedback, approving new incidents, and explaining or resolving possible matches. Related reports are blocked from ordinary publication until their relationship is resolved. The same screen includes workbook import, AI, and Telegram controls. [Admin panel](../frontend/src/components/AdminPanel.jsx), [request protection](../mcad/security.py), [relationship tests](../tests/test_candidate_relationships.py) |
| Database and historical import | SQLAlchemy uses SQLite locally and PostgreSQL in hosting. Workbook imports preserve original fields, sources, and the available date and location precision. Imports do not queue publication alerts. Explicit migrations track versions 1–6, including feedback, monitoring, candidate alerts and relationships, and incident revisions. [Importer](../mcad/import_workbook.py), [import guide](data-import.md), [migrations](../mcad/migrations/__init__.py) |
| Report ingestion | RSS polling creates pending candidates. Optional AI discovery and verification use the OpenAI Responses API and retain evidence and uncertainty on pending candidates. AI defaults off and requires explicit server and monitor settings. Saving a paused schedule does not start research. [Workers](../mcad/workers.py), [AI monitor code](../mcad/ai_monitor.py), [AI operation and limits](ai-monitor.md) |
| Telegram | Workers deliver queued publication alerts to subscribers. Eligible, source-checked AI candidates can send a separate pre-publication research alert. Related or uncertain candidates are held for review. Recipients who already received the research alert are excluded from the subsequent publication alert for that report. The default format remains a source link. [Publication delivery](../mcad/workers.py), [candidate delivery](../mcad/candidate_alerts.py), [backend guide](../mcad/README.md) |
| Hosting | Docker builds and serves the frontend with the API and workers. Railway checks `/api/health` and uses PostgreSQL. The original standalone Telegram scripts are a legacy workflow. [Dockerfile](../Dockerfile), [Railway configuration](../railway.toml), [hosting guide](hosting.md), [root README](../README.md) |

## Partially implemented and unverified

- **Existing behavior.** Commits through `7878f94` added a protected reviewed-update API. It checks that the report is pending and eligible, the target is published, and the target has the version the reviewer opened. It merges sources and records before/after snapshots, evidence, and a reason in the same transaction as the update. This path creates no Telegram alert. [API](../mcad/api.py), [update service](../mcad/service.py), [revision tests](../tests/test_incident_revisions.py)
- **Work in progress.** At inspection, the working tree contained an update comparison, target and source selection, and API wiring for pending reports flagged as related. The UI can preselect a suggested target, offers a limited set of text fields, and currently displays a save error without a dedicated reload-and-compare flow. Settings and review are still on the same screen. Browser behavior, accessibility, and the final workflow remain unverified. [Admin panel](../frontend/src/components/AdminPanel.jsx)
- **Known limitations.** Source and title matching are conservative heuristics. Opened sources and automated tests do not establish that claims are accurate or genuinely independent. Telegram can retry after a crash between sending and recording delivery. Run limits and usage records do not guarantee a dollar cap. [AI monitor guide](ai-monitor.md)
- **Needs confirmation.** The domain rules await client confirmation. Live AI access, accuracy and actual billing, scheduling in operation, and the deployed branch and settings were outside this baseline. Revision storage exists. The [incident review specification](specs/incident-review/spec.md) includes an administrator-only history view for the next release.

## Safe local development and verification

Use the [local setup](hosting.md#локальная-разработка) with a fresh SQLite database, synthetic data, and a local-only administrator token. Before starting the API, verify the effective environment points to that database, blank out OpenAI and Telegram credentials, and set the background, RSS, Telegram, and AI flags to false. Vite proxies `/api` to port 8090 locally. Keep production credentials and the real client workbook outside test fixtures.

Follow [automated checks](ci.md) for Python, frontend, PostgreSQL, and container commands. On this branch with the existing work in progress, the isolated backend run passed 89 tests with 7 opt-in PostgreSQL and private-workbook checks skipped. The frontend data suite passed 36 tests. These checks cover specific API, storage, and form behavior. They leave browser journeys, PostgreSQL in this run, and live integrations to separate verification.
